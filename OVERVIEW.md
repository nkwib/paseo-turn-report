Turn report shows which agent turns need attention. After a turn, it runs the project check you set or approved, compares the agent's claims with its recorded commands and flags merge conflicts with other live agents' worktrees. The timeline card also lists changed documents. A board shows the latest report for every agent on the host.

It is meant for running several coding agents at once, each in its own Git worktree. Everything runs on the machine with your Paseo daemon, and the plugin itself makes no network requests.

## Setup

Requires Paseo 0.11.2 or later, and Git 2.38 or later on the daemon host for conflict detection. The check needs a daemon on macOS or Linux; on Windows it does not run and the card says checks need macOS or Linux. The other sections work on every platform.

The check needs a command. Set "Check command" in Settings, Turn report, or add `scripts.verify`, `scripts.check` or `scripts.test` to the workspace's `paseo.json`. The setting wins when both exist. Without either, the card says there is no check, names both places, and the other sections still work.

A command found in `paseo.json` does not run until you approve it, because an agent can edit that file. Until then the card reads "Check needs approval" and shows the command with a "Run this check after each turn" button, on the card and on the board. Approval covers that exact command text in that workspace: when the text changes, the card asks again. A command with control, zero-width or bidirectional characters is shown with those characters escaped and cannot be approved. The "Check command" setting runs without approval, because you typed it there.

Approval pins the command text, not what it runs. An approved `npm test` or `node test.mjs` runs whatever `package.json` and the test files contain at that moment, including code the agent just wrote. The check runs that project code after every turn as the daemon's user, outside any agent sandbox, with that user's files and network. The setting behaves the same way.

## The card

A turn that completes gets a card. A turn with no shell command, no claim and no changed file (a chat-only turn) gets none, and neither does a canceled or failed turn. The top line has a chip for each section, and a proof chip when a claim needs attention.

- **Check.** The plugin runs the check in the repository root with `/bin/sh`, as the daemon's user, in its own process group. Its environment is the daemon's, plus `CI=1` and `FORCE_COLOR=0`, minus the variables Paseo removes before it starts any external process (such as `ELECTRON_RUN_AS_NODE`) and minus every `PASEO_*` variable, `PASEO_PASSWORD` included. The card shows the command, where it came from, the exit code, the duration and the last 2,000 characters of output, with Show output, Copy output and Re-run. The check ends when its shell exits; whatever it left running in its process group (a server started with `&`) is stopped then. A check that runs longer than "Stop the check after" (10 minutes by default) is stopped with its whole process group, and so is a running check when the plugin stops or reloads. Only one check runs per agent at a time: a turn that ends while the previous check still runs reads "Check busy".
- **Proof.** The plugin reads the claims in the agent's final message ("tests pass", "build ok", "verified", "fixed", "done") and judges each against every command the agent ran after its last file edit, and against the plugin's check:
  - "contradicted" (red): the agent's last matching command failed.
  - "agent and check disagree" (amber): the agent's run passed and the plugin's check failed.
  - "check failed after claim" (amber): the plugin's check failed and the agent ran nothing that settles it.
  - "unverified" (amber): "tests pass", "build ok" or "verified" with no matching command and no matching check.
  - "verified" (green): a matching command passed, or the plugin's check passed.
  - "not checked" (muted): "fixed" or "done" with nothing run and no check. A bare "done" never reads green on its own.

  A test claim needs a test command, a build claim a build command, and "verified", "fixed" and "done" accept a test, build or lint command. An unrelated command such as `ls` or `git status` settles no claim. For those three, the last run of each kind after the last edit counts: if any of them failed, the claim is contradicted, whatever passed after it. The plugin's check counts for a claim the same way: a lint check does not verify "tests pass", and a check the plugin cannot classify (`make ci`, `./check.sh`) settles no claim.

  The Check chip reports the configured shell command's exit status. Proof separately decides whether that command establishes a test, build or lint result, using the same rules as the agent's commands. A successful pipeline or help command can therefore read "Check passed" while its claim remains unverified.

  A command is classified by the program each part of it runs. The line is split at `&&`, `||`, `;`, `|` and new lines, and environment assignments, prefixes such as `timeout 60`, and runners such as `npx`, `pnpm exec`, `yarn`, `bunx`, `uv run`, `poetry run` and `python -m` are skipped, so `npx vitest run` is a test run and `cat test.mjs` or `rg -n jest` is not. A command recorded outside the agent's repository does not establish a result for it. If a provider omits each call's directory, a directory change seen in the timeline leaves later runs unverified until the provider reports their location; changes in older turns count too. Help, version, test listing, collection-only and dry-run flags do not count as runs. Known programs and scripts are recognized (vitest, jest, pytest, `cargo test`, `go test`, `npm test` and `test:*` scripts, tsc, eslint, ruff, a script named like `test.mjs`, and similar). A test, build or lint run whose exit status the line does not return reads "exit unknown" and is not evidence either way: piped into another command without `set -o pipefail` (`npx vitest run | tail -5`), followed by `||`, sent to the background with `&`, or followed by more commands. When an agent ends a command with a supported `echo "exit: $?"` form, the plugin uses the status only if it can read the corresponding output. Missing or ambiguous output reads "exit unknown"; the echo's own exit 0 never substitutes for it. A command you denied never settles a claim and does not count as a failure. A command the agent moved to the background is not evidence either way, unless a later tool call in the same turn reports its exit status. Shell writes, such as `sed -i`, a heredoc redirected to a file or `git checkout`, invalidate earlier evidence just like edit tools. A command that both writes and checks is treated conservatively. The section also counts the turn's commands, failures and denials (shell and other tools), lists the last commands with their exit codes, shows a count of the files written, lists any test files edited, and says whether the agent ran the configured check itself.
- **Collisions.** The plugin compares this agent's worktree with the worktrees of other live agents in the same repository, up to 8, and lists the files that would conflict if both were merged, with the kind of conflict (content, add/add, modify/delete). It compares the current state of each worktree, including uncommitted and untracked files, not just committed branches. The other agent's latest report is updated too, so both sides show the conflict. In a workspace that is not a Git repository the chip reads "Collisions need a git repository".
- **Documents.** PDF, Word, Excel, CSV and TSV, PowerPoint, image (including TIFF, HEIC, WebP and SVG), JSON Lines, Parquet, video, audio and Jupyter notebook files modified during the turn, newest first, up to 12, marked new or changed, with a copy path button. When the [PDF and Office viewer](https://github.com/nkwib/paseo-doc-viewer) plugin is enabled in the daemon config as the turn ends, the card and the board fold the list into one line with the count ("4 documents"), because the viewer may add its own card for the same files. The line opens the full list. The plugin cannot see whether the viewer runs, which version it is or whether it has a card for the turn, so the line says only how many documents there are. Every document is stored with the report either way, so a wrong guess changes only whether the list starts folded. A report from 0.1.x, or from a turn while the viewer was not enabled, shows the full list.

Re-run repeats the check, the conflict check and the document scan for a stored report, using the original turn's time window, and replaces the card. It keeps whether the list starts folded. A second Re-run or approval of a report while it is being redone starts nothing new, and the approve button stays disabled until the request returns.

## Board

The Turn reports item in the sidebar footer shows the most urgent count that is not zero ("2 red", "1 amber", "3 unchecked" or "4 green") and opens the board. The board fetches all kept reports and lists the latest report per agent, or every turn with History, each colored by the worst of its check, collisions and proof: a contradicted claim makes it red, an amber proof or a conflict makes it at least amber. Tap a row to see the full report and open a colliding agent. The same board is a workspace panel, limited to that workspace unless you turn on All workspaces, and the Command Center has "Open turn reports" and "Open turn report board". Open boards refresh every 4 seconds.

## Settings

Settings, Turn report, applies to the host and is shared by every client:

- Run the project check when a turn ends: on by default.
- Check command: empty by default, which means `paseo.json` (with approval).
- Stop the check after: 10 minutes by default.
- Send failures back to the agent, at most: "Never send" by default, or 1, 2, 3 or 5 times. See below.
- Check conflicts with other live agents: on by default.
- List documents changed during the turn: on by default.
- Document viewer plugin: `paseo-doc-viewer` by default. While that plugin is enabled, the documents list starts as one line with the count. Empty never folds the list.

## Messages sent to agents

By default the plugin never sends anything to an agent. When "Send failures back to the agent" is above zero and the check fails, the plugin sends the agent one message with the command, its exit code and the last 2,000 characters of output, and asks it to fix the cause. It sends only if the agent is idle right before sending, and the card says "not sent" otherwise. One gap remains: if a turn starts in the moment between that check and the send, the daemon adds the message to the running turn on providers that can steer, and replaces the turn on the others. After the set number of failed checks in a row it stops and the card says it gave up. The message becomes part of that agent's conversation and reaches the agent's model provider, so anything your check prints, including secrets, goes with it.

## What it reads and runs

- The agent's conversation, which Paseo passes to the plugin when a turn ends. The plugin keeps only facts from the current turn.
- The host's agent list (titles, working directories, status), to find live agents in the same repository.
- The daemon configuration, when a turn ends, to tell whether the document viewer plugin is enabled. Only its plugin entries are used.
- The workspace's `paseo.json`, file names, sizes and times in the workspace, and Git change lists. The document walk reads metadata; Git compares tracked file contents with `HEAD`.
- Git, run on the daemon host with prompts, pagers, optional locks, lazy fetching and the fsmonitor hook turned off, with the same environment cleanup as the check, and without variables such as `GIT_DIR` that would point it at another repository. On the repository itself it runs `rev-parse` and `config` to read the object format, safe filesystem and line-ending settings, and the configured ignore-file path. Passive `diff`/`ls-files` and conflict detection run against private repositories under the system temp directory (`turn-report-*`): their own config and index, the repository's objects read through alternates, and a copy of `info/exclude`. Global and system Git config are disabled there; only those safe settings are carried over. Parent diff does not enter dirty submodule worktrees. No configured clean/process filter or merge driver runs. In-tree `.gitignore` and `.gitattributes` still apply, but a custom driver named in attributes is undefined and Git uses its built-in behavior. Conflict detection also runs `read-tree`, `add`, `write-tree`, `commit-tree` and `merge-tree` in that private repository. The temporary repositories are deleted afterwards. The plugin never writes to your worktrees, their index, branches or the repository's objects.
- The check command, as described above. It runs project code, including code the agent just wrote, and can do anything the daemon's user can.
- Approving a `paseo.json` check goes through a plugin RPC, which any client connected to the daemon can call. The plugin offers it on the card and on the board.

## What it stores

Reports are stored on the daemon host in `$PASEO_HOME/plugin-data/turn-report` when the daemon's environment sets `PASEO_HOME`, otherwise in `paseo-turn-report` under `$XDG_STATE_HOME` (`~/.local/state` by default). The folder is readable only by the daemon's user. If it is a symlink or belongs to another user, the plugin keeps reports and approvals in memory only. `reports.json` keeps the last 200 reports, so the board survives restarts. A report holds the agent's id, title and provider, the workspace id, the repository path and branch, the check command, exit code and last 2,000 characters of output, conflicting file paths and the other agents' titles, document paths and sizes, up to 12 of the turn's shell commands in full (the ones the verdicts rest on, then the latest), up to 20 written file paths and any test files edited, the names and file paths of denied tools, the first line of failed tool errors, and each claim sentence (up to 90 characters) with its verdict and reason. A file the plugin cannot read, or one written by a newer version, is moved aside (`reports.json.bad`, or a name with its version such as `reports.json.v4`) before a new one is written. Check approvals are kept in `check-approvals.json` in the same folder, as salted hashes of the workspace path and the command, up to 200. To clear everything, delete the folder while the daemon is stopped.

Saved reports and timeline cards from 0.1.0 keep their check results, commands and failures, but old passing proof verdicts read "not checked" after upgrading. Re-run uses the current rules and a fresh project check; it cannot recover command output that was never saved.

The cards themselves live in the agent's timeline, which Paseo keeps in the daemon's memory, so they disappear from the chat after a daemon restart. The board keeps them.

## Limits

- Passive Git reads omit `info/attributes` and configured filter/merge drivers. Repositories that rely on them can show extra changed files or different conflict results. The workspace's ignore files, `info/exclude`, configured global ignore file and safe line-ending settings still apply.
- Changed files come from `git diff HEAD` and untracked entries modified during the turn, plus the files the agent's edit tools report. Git sees every change in that window, not only this agent's: a change by you, by another agent in the same worktree, or a file the previous turn's check wrote counts as this turn's, and can give a chat-only turn a card. The documents list has the same limit.
- Denials by Claude Code and OpenCode are recognized by Paseo's standard deny messages. A denial with a custom message reads as a failed command, which can mark a claim contradicted. Codex marks denials explicitly.
- Shell write detection is conservative: a redirect or `tee` into any file, including a log or a file under `/tmp`, ends the evidence scope. A write and a check on the same shell line leave that line unverified. Writes hidden inside a script or performed by the test itself, including snapshot updates, are not detected. A directory change missing from the host's supplied timeline cannot be inferred.
- Command names and exit statuses are evidence, not test-result parsing. A recognized test command that exits 0 without running tests, for example with `--passWithNoTests`, can still support a claim.
- Claims are matched in English, in the agent's final message only, one per kind. Sentences that hedge, negate or plan ("should pass", "not fixed", "won't", "haven't run") are ignored; a zero count such as "0 failed" is not a negation.
- A claim about some tests ("unit tests pass") is judged against the last test command of any scope: a failing `npm test` that also runs end-to-end tests contradicts it.
- A test script with an unusual name (`node smoke.mjs`, `./ci.sh`) counts as an "other" command and settles no claim, whether the agent or the plugin runs it.
- A process the check starts in a new session leaves its process group: it keeps running after the check ends or times out, though the check no longer waits for it.
- The turn is cut from the conversation by position, because timeline items carry no time. For the first turn after the plugin starts it begins at the last user message. A turn already running when the plugin started gets no document list.
- Conflicts are checked only between worktrees of the same repository. Agents sharing one worktree are not compared with each other.
- A plugin can read which plugins the daemon config enables, not which ones run or which version has a turn card. With the viewer enabled but not running, or too old to add a card, the list still starts folded: open it to see the documents.
